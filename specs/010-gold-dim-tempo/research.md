# Research: Gold Calendar Dimension

**Feature**: [spec.md](spec.md) | **Date**: 2026-11-05

Sources: constitution v2.0.0; `databricks-dbsql` skill, `references/sql-scripting.md`
(DDL and DML inside `BEGIN … END`); the existing calendar cell in
`explorations/functions.py` (lines 512–608); the setup scripts
`explorations/setup/01_schemas.sql` and `02_landing_volume.sql`; `doc/known-issues.md`;
the workspace on 2026-11-05 (`workspace.gold` holds only `dim_usuario`).

No item of the Technical Context was left as NEEDS CLARIFICATION.

## Decision 1: Where the calendar is built

- **Decision**: a setup script, `explorations/setup/04_dim_tempo.sql`, run by hand with
  `databricks experimental aitools tools query <file> --profile <profile>`, like steps 01
  and 02.
- **Rationale**: the owner asked for a one-time script. The constitution allows static
  reference data, naming the calendar as the example, to be loaded by an idempotent script
  outside the pipeline (Principle I). The pipeline does not need the file to be deployed,
  so it is auxiliary code and belongs in `explorations/setup/` (Repository layout). `04` is
  the next free step number.
- **Alternatives considered**:
  - A pipeline materialized view: rebuilt on refresh, so an identity key could be
    reassigned (Principle VII), and the owner asked for a script.
  - Keeping the cell in `functions.py`: it is the source of the known issue, and it runs
    every time the generators are loaded.

## Decision 2: One compound statement

- **Decision**: the script is a single `BEGIN … END` block with `DECLARE`, `CREATE TABLE IF
  NOT EXISTS`, two `INSERT … WHERE NOT EXISTS`, a duplicate check with `SIGNAL`, and a final
  summary `SELECT`.
- **Rationale**: the query tool runs one statement per call; `02_landing_volume.sql`
  already uses a compound block for the same reason. SQL scripting accepts DDL
  (`CREATE`) and DML inside the block (skill reference, "Statement types").
- **Alternatives considered**: several statements run one by one (more steps for whoever
  runs it, and a partial run is easier to leave behind); a stored procedure (a catalog
  object nobody needs to call twice).

## Decision 3: Idempotency by inserting only what is missing

- **Decision**: days are inserted with `WHERE NOT EXISTS` on `data`; members with `WHERE
  NOT EXISTS` on `sk_tempo`. Existing rows are never updated or deleted.
- **Rationale**: a second run inserts nothing, so row count, keys and `data_carga` stay the
  same (FR-005, SC-003). Moving the end date forward later adds only the new days (spec,
  edge case). An identity value is never regenerated for an existing day, which is what
  keeps the key stable (FR-004).
- **Alternatives considered**: `MERGE … WHEN NOT MATCHED THEN INSERT` (same result, harder
  to read for two inserts); `CREATE OR REPLACE` / `INSERT OVERWRITE` (rebuilds the table and
  reassigns every identity key, which breaks Principle VII).

## Decision 4: Stop on repeated days

- **Decision**: before inserting, the script counts days that appear more than once and
  stops with `SIGNAL SQLSTATE '45000'` if any do, naming the problem and telling the reader
  that the table must be dropped with the owner's approval.
- **Rationale**: a table left by the old `functions.py` cell can hold repeated days.
  Inserting the missing ones would report success over a broken table. The script never
  drops the table itself: a table drop is the user's decision (Development Workflow).
  In the current workspace the table does not exist, so this never fires there.
- **Alternatives considered**: deleting duplicates in the script (rewrites rows, and which
  copy's key survives is arbitrary); ignoring them (silently multiplies fact rows).

## Decision 5: Identity column as requested

- **Decision**: `sk_tempo BIGINT GENERATED BY DEFAULT AS IDENTITY`, exactly as the owner
  wrote it. Defaults are `START WITH 1 INCREMENT BY 1`, so day keys are positive. The
  members are inserted with explicit values `-1` and `-2`, which `BY DEFAULT` permits.
- **Rationale**: `BY DEFAULT` (not `ALWAYS`) is what lets the members carry fixed negative
  keys. Explicitly inserted values do not move the identity's high-water mark, but they are
  negative and generated values are positive, so they cannot collide. Identity values are
  unique but not guaranteed consecutive or in date order, which the spec allows.
- **Alternatives considered**: `GENERATED ALWAYS` (rejects the explicit member keys); a
  date-derived key such as `yyyymmdd` (deterministic, but not what the owner asked for).

## Decision 6: Attribute expressions

- **Decision**:

  | Column | Expression |
  |---|---|
  | `ano` | `year(data)` |
  | `mes` | `element_at(array('janeiro', …, 'dezembro'), month(data))` |
  | `mes_ano` | `month(data)` |
  | `dia_semana_int` | `dayofweek(data)` (1 = Sunday) |
  | `dia_semana` | `element_at(array('domingo', 'segunda-feira', …, 'sábado'), dayofweek(data))` |
  | `fl_dia_semana` | `dayofweek(data) BETWEEN 2 AND 6` |
  | `dia_mes` | `dayofmonth(data)` |
  | `fl_ultimo_dia_mes` | `data = last_day(data)` |
  | `dia_ano` | `dayofyear(data)` |
  | `semana_ano` | `weekofyear(data)` (ISO week) |
  | `bimestre` | `CAST(ceil(month(data) / 2) AS INT)` |
  | `trimestre` | `quarter(data)` |
  | `semestre` | `CAST(ceil(month(data) / 6) AS INT)` |
  | `data_carga` | `current_timestamp()` |

- **Rationale**: same meanings as the existing cell (spec, Assumptions), written more
  simply. Explicit name arrays replace `to_csv(..., map('locale', 'PT'))`: the output no
  longer depends on the Java locale data, and the names are visible in the code.
- **Alternatives considered**: keep `to_csv` with the PT locale (opaque; capitalization and
  accents depend on the runtime); keep the `CASE` ladders (correct, five times longer).

## Decision 7: Members

- **Decision**: `-1` with `mes` = `dia_semana` = `Desconhecido`; `-2` with `Não se aplica`;
  `data` and the other attributes `NULL`; `data_carga` = insert time.
- **Rationale**: FR-006; same keys and labels as `dim_usuario`. A null `data` never matches
  a fact's date, so a fact resolves to `-1` through `coalesce`.

## Decision 8: Removing the old calendar cell

- **Decision**: delete the last cell of `explorations/functions.py` (the `# COMMAND
  ----------` separator at line 512 through line 608), and nothing else in that file.
- **Rationale**: FR-009. `explorations/user_case.py` runs `functions.py` with `%run`, so
  removing the cell is what stops the generators from appending calendars.

## Decision 9: The period

- **Decision**: 2021-01-01 to 2030-12-31, 3,652 days, held in `v_inicio` and `v_fim`.
- **Rationale**: set by the owner on 2026-11-05 (spec, Clarifications). It covers the
  generated sales and accesses (2024-06-01 to 2025-12-31) and leaves room for new data
  until 2030 without rerunning the script.
- **Alternatives considered**: the old cell's 2024-06-01 to 2026-12-31 (ends in eight
  weeks); deriving the end from `current_date()` (a later run would add days, and the
  row count would depend on when the script ran).

## Decision 10: Validation without a test framework

- **Decision**: run the script twice and compare with queries ([quickstart.md](quickstart.md)).
  The script's final `SELECT` reports rows, days, members, first and last day, and
  repeated days, so each run shows its own result.
- **Rationale**: the project has no test framework (as in features 001–009); a separate
  verify script would duplicate the summary for a table this small.
