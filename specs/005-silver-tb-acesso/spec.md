## User Scenarios & Testing *(mandatory)*

### User Story 1 - One conformed row per valid site access (Priority: P1)

As the project owner, I want every valid site access from the API to become one row of a
conformed silver table, `workspace.silver.tb_acesso`, with a readable access time, the
address it came from and the kind of device it came from, so that later analyses of site
traffic start from clean, typed data.

The table reads only the events that passed the validation of feature 004. Events in
quarantine never reach it.

**Why this priority**: the access table is the first conformed silver table of the API
source, and the gold access analysis depends on it.

**Independent Test**: after a run, compare `tb_acesso` with the valid events of the
validation step. Every valid event with a usable address is present once, its time is a
real timestamp, and its device is classified as the mapping says.

**Acceptance Scenarios**:

1. **Given** a valid API event, **When** the run completes, **Then** `tb_acesso` holds
   one row for it with `timestamp_acesso` equal to its access time read as a timestamp.
2. **Given** a valid event whose device is `iphone` or `android`, **When** it is loaded,
   **Then** its `local_acesso` is `Mobile`.
3. **Given** a valid event whose device is `chrome`, `safari`, `firefox` or another web
   browser, **When** it is loaded, **Then** its `local_acesso` is `Computador`.
4. **Given** a valid event whose device is `unknown`, empty or any value not recognized,
   **When** it is loaded, **Then** its `local_acesso` is `unknown`.
5. **Given** a valid event, **When** it is loaded, **Then** `endereco_ip_acesso` holds the
   address the access came from, unchanged.
6. **Given** an event in quarantine, **When** the run completes, **Then** it is not in
   `tb_acesso`.

### User Story 2 - Reject impossible addresses and measure unknown devices (Priority: P1)

As the project owner, I want accesses from the impossible address `999.999.999.999` kept
out of the access table. I also want accesses from unrecognized devices counted, without
removing them, and the stricter rule that would stop the run on them visible in the
definition but switched off. That way the talk can show the three actions an expectation
can take.

**Why this priority**: the two rules are the point of this table in the demonstration,
and the address rule decides which rows the table holds.

**Independent Test**: after a run, the pipeline's data quality view shows both rules by
name. The address rule's failed count equals the number of valid events with address
`999.999.999.999`, none of which is in the table. The device rule's failed count equals the
number of rows whose `local_acesso` is `unknown`, all of which are in the table.

**Acceptance Scenarios**:

1. **Given** a valid event with address `999.999.999.999`, **When** the run completes,
   **Then** it is not in `tb_acesso` and is counted as a failure of
   `check_endereco_ip_acesso`.
2. **Given** a row whose `local_acesso` is `unknown`, **When** the run completes, **Then**
   it is in `tb_acesso`, counted as a failure of `check_local_acesso`, and the run does not
   stop.
3. **Given** the definition of `tb_acesso`, **When** it is read, **Then** the rule that
   would stop the run on an `unknown` device is present as a comment, ready to be switched
   on.
4. **Given** events removed by `check_endereco_ip_acesso`, **When** the owner looks for
   them, **Then** they are not in quarantine. Their number is the rule's failed count, and
   the project documentation lists the rule as a declared exclusion of the API source.
   The events themselves remain in bronze.
5. **Given** the three rules of the table, **When** the talk shows them, **Then** each
   expectation action appears once: removing a row (`check_endereco_ip_acesso`), counting
   only (`check_local_acesso`), and stopping the run (commented).

### User Story 3 - Stable keys to the access, the user and the course (Priority: P1)

As the project owner, I want every access row to carry a deterministic key for itself and
the keys of the user and the course it refers to. Gold can then join accesses to users and
courses, and reprocessing the same event always yields the same keys.

**Why this priority**: without the keys, gold cannot link accesses to the other
entities, and the constitution requires a hash key on every conformed silver table.

**Independent Test**: recompute the three keys from the source fields of a sample of rows
and compare them with the stored values. Check that `acesso_uuid` is never empty, and that
`curso_uuid` matches the course identifier of the course catalog for every row with a
product.

**Acceptance Scenarios**:

1. **Given** an access row, **When** its `acesso_uuid` is recomputed from
   `timestamp_acesso`, the address and `local_acesso`, **Then** it equals the stored value.
2. **Given** an event with a user, **When** its `usuario_uuid` is recomputed from
   `timestamp_acesso` and the user's name, **Then** it equals the stored value.
3. **Given** an event with a product, **When** its `curso_uuid` is compared with the course
   catalog, **Then** it equals the catalog's identifier for that course name.
4. **Given** an event without a user or without a product, **When** it is loaded, **Then**
   `usuario_uuid` or `curso_uuid` is empty, because there is nothing to refer to.
5. **Given** the same event processed twice (after a full refresh), **When** the keys are
   compared, **Then** they are identical.
6. **Given** every row, **When** it is read, **Then** `origem` is `API` and `data_carga`
   holds the time the row was loaded.

### Edge Cases

- An access with no payload (a visit without login or purchase): it is a valid access.
  `usuario_uuid` and `curso_uuid` are empty, and `acesso_uuid` is still set.
- A device value with different casing (`IPhone`, `Chrome`): treated as the same device.
  The mapping ignores case.
- A device value the mapping does not know (a new browser): `unknown`. It is kept, and
  counted by `check_local_acesso`.
- An address that is malformed but not `999.999.999.999`: kept. Only the exact value given
  in the request is rejected.
- An access time that cannot be read as a timestamp: not expected from the generator. If it
  occurs, the row keeps an empty `timestamp_acesso` and the planning phase decides how it
  is measured. It is not silently dropped.
- Two events with the same time, address and device (for example a re-delivered bronze
  file): they produce the same `acesso_uuid`. The constitution requires the key to be
  unique in the table, so planning must check whether this happens in the data and, if it
  does, deduplicate on the key.
- An event later moved to quarantine by a change of the validation rules: it stays in
  `tb_acesso` until the owner approves a refresh.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The feature MUST provide a conformed silver table `workspace.silver.tb_acesso`,
  fed incrementally from the valid events of the API validation step (feature 004): those
  whose `fl_registro_invalido` is false. It MUST NOT read quarantined events or bronze
  directly.
- **FR-002**: The table MUST have exactly these columns:

  | Column | Type | Content |
  |---|---|---|
  | `timestamp_acesso` | TIMESTAMP | the event's access time (`access_date`) read as a timestamp |
  | `endereco_ip_acesso` | STRING | the event's address (`ip_address`), unchanged |
  | `local_acesso` | STRING | `Mobile` for `iphone` or `android`; `Computador` for `chrome`, `safari`, `firefox` or another web browser; `unknown` for anything else, including `unknown` and empty |
  | `acesso_uuid` | STRING | key of the access, derived from `timestamp_acesso`, the address and `local_acesso` |
  | `usuario_uuid` | STRING | key of the user, derived from `timestamp_acesso` and `payload.info_usuario.nome`; empty when the event has no user |
  | `curso_uuid` | STRING | key of the course, derived from `payload.info_produto.product_name`; empty when the event has no product |
  | `origem` | STRING | the literal `API` |
  | `data_carga` | TIMESTAMP | when the row was loaded |

- **FR-003**: The three keys MUST follow the constitution's hash key rule (Principle VI):
  deterministic, computed only from the listed fields, with no load time or random input,
  so that reprocessing yields the same value.
- **FR-004**: `curso_uuid` MUST equal the course identifier delivered by the course
  catalog for the same course name, so that the table joins the course table and the
  course dimension.
- **FR-005**: `usuario_uuid` and `curso_uuid` MUST each be defined once in the pipeline and
  reused by every later table that refers to a user or a course from the API source.
- **FR-006**: The table MUST declare the rule `check_endereco_ip_acesso`: the address is
  not `999.999.999.999`. A row that fails it MUST be removed from `tb_acesso`.
- **FR-007**: A row removed by `check_endereco_ip_acesso` MUST NOT be routed to quarantine.
  The drop is a declared exclusion under constitution v1.7.0 (Principle IV): the plan names
  the rule and its reason, the rule's failed count records how many rows were dropped, and
  `doc/pipeline-reference.md` lists it as a reconciliation exclusion of the API source.
- **FR-008**: The table MUST declare the rule `check_local_acesso`: `local_acesso` is not
  `unknown`. A failure MUST only be counted: the row stays and the run continues.
- **FR-009**: The definition MUST contain, as a comment next to `check_local_acesso`, the
  same rule with the action that stops the run, so that it can be switched on by removing
  the comment.
- **FR-010**: The table MUST declare that `acesso_uuid` is never empty, as the constitution
  requires for a conformed table's hash key, and `acesso_uuid` MUST be unique in the table.
- **FR-011**: Every rule MUST state how it treats an empty value. An empty address passes
  `check_endereco_ip_acesso`; an empty device becomes `unknown` and fails
  `check_local_acesso`.
- **FR-012**: The table MUST carry the table property `quality` with the value `silver`.
- **FR-013**: Events already loaded MUST NOT be loaded again by a later run.
- **FR-014**: For the API source, valid events MUST equal rows in `tb_acesso` plus rows
  removed by `check_endereco_ip_acesso`.
- **FR-015**: The definition MUST follow the constitution: SQL, current syntax, declared as
  streaming (silver), one file named `NN_tb_acesso.sql` in the silver folder.
- **FR-016**: The table, its columns, keys and rules MUST be described in the project
  documentation, replacing the description of the earlier pipeline. The business key
  columns behind each hash key MUST be listed there.

### Key Entities

- **Access** (`tb_acesso` row): one valid visit to the site, with when, from which
  address and from which kind of device, identified by `acesso_uuid`.
- **User reference** (`usuario_uuid`): the user the visit belongs to, when the visit
  carries a user. It points to the user entity of later features.
- **Course reference** (`curso_uuid`): the course the visit concerns, when it carries a
  product. It points to the course catalog (`tb_curso`) and the course dimension.
- **Device category** (`local_acesso`): `Mobile`, `Computador` or `unknown`, derived from
  the raw device value.
- **Access rules**: `check_endereco_ip_acesso` (removes the row), `check_local_acesso`
  (counts only, with the stopping variant commented), and the not-empty rule on
  `acesso_uuid`.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: After a run, valid events = rows in `tb_acesso` + events removed for the
  impossible address, with a difference of 0.
- **SC-002**: 0 rows in `tb_acesso` have the address `999.999.999.999`.
- **SC-003**: 100% of rows have `local_acesso` in {`Mobile`, `Computador`, `unknown`}, and
  for a sample of each raw device value the category matches the mapping.
- **SC-004**: The quality view lists `check_endereco_ip_acesso`, `check_local_acesso` and
  the key rule, each with failed counts equal to those computed directly from the valid
  events.
- **SC-005**: 100% of rows have a non-empty `acesso_uuid`, and no two rows share one.
- **SC-006**: For 100% of rows with a product, `curso_uuid` matches an identifier in the
  course catalog.
- **SC-007**: 100% of rows have `origem` = `API` and a non-empty `data_carga`.
- **SC-008**: A second run with no new events adds 0 rows.

## Assumptions

- "Drop the row" means the expectation action that removes the row from the table.
  The owner chose (2026-10-18) not to quarantine these rows: "Not all constraints need to
  go to the quarantine table. I want to show the idea behind each of the cases." The
  constitution was amended to v1.7.0 to allow this as a declared exclusion. The validation
  step of feature 004 keeps quarantining its own rejections.
- "Keep commented the rule to fail update" means the stopping version of
  `check_local_acesso` is present in the file as a SQL comment, not active.
- "Other web browser" covers `chrome`, `safari` and `firefox`, the browser values the
  generator produces. The mapping ignores case.
- "uuid" means the constitution's hash key: an `md5` text of 32 hex characters, not a
  random UUID. Random values would break reprocessing.
- `ip_address` in the key of `acesso_uuid` is the same value as `endereco_ip_acesso`.
- `curso_uuid` is the `md5` of the product name alone. This was checked on 2026-10-18:
  `md5('Construindo um Data Lakehouse com SQL e DLT')` equals the `curso_uuid` delivered by
  the course catalog (`6532cdca76d4a7e6f10f71be7eb74668`), so the keys join.
- A reference key is empty when the referenced entity is absent (no user, no product). The
  constitution's placeholder-for-null rule applies to the components of a key that exists;
  inventing a user key for a visit without a user would create users who do not exist.
- `usuario_uuid` includes the access time, as requested and as in the earlier pipeline.
  The same person therefore gets a different key on each visit. This matches the request,
  and later user tables must reuse the same expression.
- "Following the principle of data vault" for `origem` means the constitution's record
  source rule: the literal `API`, set by the flow that reads the source.
- Only the API source feeds `tb_acesso`; partner file sales carry no access events.
- The validation step of feature 004 is deployed, and its rules stay as they are.
- The environment is Databricks Free Edition. All data is synthetic. About 1% of generated
  events carry the address `999.999.999.999`.
